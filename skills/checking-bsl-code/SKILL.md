# Проверка кода BSL Language Server

## Запуск

```bash
node <каталог этого скилла>/scripts/bsl-check.mjs --src <каталог расширения> --changed <база ветки>
```

- `--src` — корень выгрузки в XML (каталог с `Configuration.xml`): расширение или
  конфигурация. Можно указать несколько.
- `--changed main` — замечания только по файлам, изменённым относительно ревизии, и новым.
  Для своей доработки — всегда с ним: старый код проекта не задача этой правки.
- `--fail-on` — с какого уровня код выхода 1; по умолчанию `error`.
- Настройки — `.bsl-language-server.json` в корне проекта, если он есть, иначе
  [bsl-language-server.json](bsl-language-server.json) скилла (правила по умолчанию,
  код на поддержке поставщика без права изменения не проверяется).
- Отчёты — в `logs/bsl/` текущего каталога (`--out`), каталог в git не идёт.

Первый запуск скачивает закреплённую версию BSL LS в кэш пользователя со сверкой sha256:
jar при Java 17+, иначе сборку со встроенной Java (около 170 МБ). Без интернета — путь
к своему BSL LS в `--bsl-ls` или переменной `BSL_LANGUAGE_SERVER`. Справка — `--help`.

Анализ большой конфигурации идёт минуты; для доработки указывать каталог расширения,
а не всей конфигурации.

## Как читать

Строка замечания — `файл:строка:колонка: уровень Код: текст`, последняя строка — итог по
уровням. Код выхода: 0 — замечаний уровня `--fail-on` и выше нет, 1 — есть, 2 — анализ не
запустился (текст ошибки в stderr).

Описание правила — `https://1c-syntax.github.io/bsl-language-server/diagnostics/<Код>`:
там пример плохого и хорошего кода и ссылка на стандарт 1С, если правило из стандартов.

## Что делать с замечаниями

| Уровень | В своём новом или изменённом коде | В коде, которого правка не касалась |
| --- | --- | --- |
| `error` | исправить до «Готово» | показать человеку, не трогать |
| `warning` | исправить, если правка небольшая; иначе показать человеку | не трогать |
| `information`, `hint` | по стилю проекта; не гнаться | не трогать |

После исправления — запустить снова и тесты тоже: правка ради анализатора меняет код.

Правило не глушить: ни комментарием `// BSLLS:<Код>-off`, ни выключением в настройках —
без согласия человека. Согласованное исключение для всего проекта — в
`.bsl-language-server.json` проекта, с причиной в сообщении коммита.

## Частые ложные и спорные срабатывания

- `CommonModuleInvalidType` — набор флагов общего модуля не совпадает со стандартными
  видами (например, серверный модуль без «Внешнее соединение»). Для модулей тестов YAxUnit
  и сервисных модулей расширения это обычно осознанный выбор: согласовать отключение
  правила в проекте.
- `QueryParseError` — текст запроса собирается динамически, анализатор его не разобрал.
- Транзакции (`BeginTransactionBeforeTryCatch`, `CommitTransactionOutsideTryCatch`,
  `WrongUseOfRollbackTransactionMethod`, `PairingBrokenTransaction`) — обычно настоящее
  нарушение стандарта: `НачатьТранзакцию()` перед `Попытка`, `ЗафиксироватьТранзакцию()`
  последним в `Попытка`, `ОтменитьТранзакцию()` первым в `Исключение`.
- `DeprecatedMethodCall` — замена может требовать более нового режима совместимости:
  сверить с режимом совместимости расширения, прежде чем менять.
