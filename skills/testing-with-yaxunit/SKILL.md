# Тесты YAxUnit

Значения машины — платформа, база, пользователь, каталог логов, имена расширений — лежат
в `AGENTS.md` проекта, раздел «Окружение 1С». Раздела нет — заполнить его вместе
с человеком по [references/environment.md](references/environment.md) и только потом
выполнять команды. Сами команды — там же.

## Подключение (один раз)

1. Взять официальный релиз с GitHub `bia-technologies/yaxunit`, совместимый с платформой,
   положить `.cfe` в репозиторий вне исходников (`vendor/yaxunit/`). Версию и sha256
   записать в `AGENTS.md`. Файл чужой: не выгружать в XML, не править, не обновлять без
   отдельной задачи.
2. Загрузить движок в базу и снять с него безопасный режим и защиту от опасных действий.
   Без этого движок не прочитает конфиг и не запишет отчёт.
3. Создать расширение тестов — отдельное от расширений продукта, исходниками рядом с ними.
   Загрузить, снять защиту: тесты пишут и удаляют данные.
4. Конфиги запуска: по одному на уровень и общий (раздел «Запуск»).
5. Проверить цепочку: один тест проходит, один падает на своём утверждении — отчёт
   и код 1. Потом проверочные тесты убрать, прогон — код 0, коммит.

Сигнатуры методов сверять по исходникам того же тега (`exts/yaxunit/src` на GitHub), а не
по памяти и не по сайту документации: сайт бывает новее релиза. Вспомогательное сначала
искать там (`ЮТест`, `ЮТТесты`, `ЮТТестовыеДанные`).

## Модуль

Тесты — общие модули расширения тестов: `Сервер` включён, `Глобальный` и `Вызов сервера`
выключены. С `Глобальный` или `Вызов сервера` YAxUnit модуль тестовым не считает и молча
пропускает. Тесты, которые читают или пишут базу, — серверные (`ДобавитьСерверныйТест`).

Уровень — тег на модуле до первого набора: `ЮТТесты.Тег("Юнит")` — правило без базы,
`ЮТТесты.Тег("Интеграция")` — запись и чтение базы. Имя набора — что проверяем, имя
теста — правило: `Метод_Уточнение`, представление `Метод(). Уточнение`.

```bsl
Процедура ИсполняемыеСценарии() Экспорт

	ЮТТесты
		.Тег("Юнит")
		.ДобавитьТестовыйНабор("Общий модуль ИмяМодуля. Метод()")
			.ДобавитьСерверныйТест("Метод_Уточнение", "Метод(). Уточнение");

КонецПроцедуры
```

Тест видит только экспортные методы проверяемого модуля: тест лежит в другом расширении.
Проверяемое правило выносить в экспортную функцию — это нормально. Менеджер основной
конфигурации — в квадратных скобках (`Справочники["Имя"]`), чтобы проверка модулей не
требовала заимствования.

Синтаксический контроль расширения тестов в Конфигураторе пишет «Переменная не
определена» на `ЮТТесты` и `ЮТест`: проверка не видит расширение движка. В сеансе
Предприятия вызов проходит — эти строки не переписывать. Но настоящая ошибка компиляции
попадает в тот же список, и тогда YAxUnit модуль пропускает (раздел «Итог»).

## Данные и проверки

Конструктор `ЮТест.Данные().КонструкторОбъекта(...)`: важные для теста поля —
`Установить`, остальные обязательные — `ФикцияОбязательныхПолей`, необязательные пустые не
заполнять. Справочную запись, без которой объект не записать, найти в базе, подставить
ссылкой и не менять; ссылку задать до фикции, иначе фикция создаст новый объект.

Табличную часть заполнять одним вызовом `ТабличнаяЧасть("Имя")` и добавлять строки
подряд: повторный вызов для той же части очищает уже подготовленные строки.

На модуле или тесте с базой — `.УдалениеТестовыхДанных()`: созданное конструктором
удаляется и после упавшего утверждения. Созданное проверяемым кодом конструктор не видит:
запомнить и до утверждений вызвать `ЮТест.Данные().ДобавитьКУдалению(...)` — ссылку
объекта или ключ записи регистра. `ДобавитьКУдалению` заменяет переданную переменную
массивом: передавать копию, если переменная нужна дальше.

Если проверяемый код сам открывает транзакцию — `.ВТранзакции(Ложь)`: вложенная транзакция
YAxUnit ломает откат, удаление тогда только через `УдалениеТестовыхДанных`.

Записи в таблице базы — `ЮТест.ОжидаетЧтоТаблицаБазы("Вид.Имя")` с предикатом
`ЮТест.Предикат().Реквизит("Поле").Равно(...)`. Поля результата —
`ЮТест.ОжидаетЧто(Значение).Свойство("Поле").Равно(...)`.

HTTP-сервис: обработчик передаёт запрос в общий модуль, тест вызывает модуль с
`ЮТест.Данные().HTTPСервисЗапрос()` (`.Метод`, `.ДобавитьЗаголовок`,
`.УстановитьТелоКакСтрокуJSON`). Публикация для такого теста не нужна.

## Red → Green

Red — тест упал **на своём утверждении**: заглушка проверяемого кода возвращает пустой
результат (`Новый Структура`, пустое значение, для HTTP — ответ с кодом успеха и пустым
телом по контракту), и `ОжидаетЧто` сообщает «ожидалось X, а было Y».

Не Red, а сломанный тест — исключение «не реализовано», ошибка компиляции, падение на
подготовке данных, неверно записанное ожидание. Такой тест чинить, а не реализовывать
под него код.

Green — тот же тест с тем же ожиданием. Ожидание берётся из требования; если код даёт
другое значение, это находка, о которой сообщают человеку, а не повод поправить тест.

## Запуск

Прогон ничего не загружает: после правки расширения — загрузка и снятие защиты, потом
прогон. Перед загрузкой закрыть клиенты 1С этой базы. Команды — в
[references/environment.md](references/environment.md).

Конфиг уровня (JSON в репозитории, рядом с тестами):

```json
{
  "filter": { "extensions": ["<расширение тестов>"], "tags": ["Юнит"] },
  "reportFormat": "jUnit",
  "reportPath": "<логи>/yaxunit/юнит.xml",
  "exitCode": "<логи>/yaxunit/юнит-exit.txt",
  "closeAfterTests": true
}
```

Общий — тот же без `tags`. Без фильтра по расширению в прогон попадают тестовые модули
других расширений. Один тест — отдельный конфиг с `"tests": ["ИмяМодуля.ИмяМетода"]`
в `filter`; общий не править.

## Итог

Итог — по отчёту, а не по окну 1С и не по одному коду:

- в файле `exitCode` 0 — тесты прошли, 1 — есть падения (текст — `failure` в jUnit);
- модуль с ошибкой компиляции YAxUnit пропускает, и код остаётся 0: сверять число тестов
  в отчёте с числом зарегистрированных;
- отчёт должен быть свежим — проверить время файла, а не только содержимое.

Человеку показать прогон можно в 1С: раздел «YAxUnit», «Запустить все тесты».
